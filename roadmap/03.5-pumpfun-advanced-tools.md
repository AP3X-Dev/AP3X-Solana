# PRP-03.5 — Pump.fun advanced tooling

**Repo:** `ap3x-solana/` (continues from PRP-03)
**Depends on:** PRP-03 (execution + safety — receipts, policy engine, audit log)
**Unblocks:** strategy authors targeting pump.fun launches (pre-PRP-08)
**Estimate:** 1-2 weeks solo
**Master spec:** [00-master-platform-prp.md](./00-master-platform-prp.md)

## Goal

Ship the **power-user tooling** for pump.fun launches that sits beside the core write path: vanity mint addresses, atomic launch-and-snipe bundles, metadata management + authority revocation, and airdrop distribution. None of this is on the trading hot path — it's separate capability surfaces that wrap PRP-03's execution primitives and ride the same safety rails (receipts, policy, audit log, thesis).

This PRP exists because pump.fun launches have specific operator tooling expectations that standard trade execution doesn't cover. Without it, users drop out to third-party tools at exactly the moment they most want to be inside our policy + audit surface. With it, every launch operation — from picking a vanity address to revoking mint authority to airdropping to holders — runs through the receipt + policy + thesis stack.

## In scope

### Package `@ap3x/pumpfun-vanity` (new)

- **Keypair grinder** — generate Solana keypairs until the pubkey matches a user-specified prefix / suffix / regex pattern. Single-threaded TypeScript baseline (using `@noble/ed25519`); optional `solana-keygen grind` shell-out for CUDA acceleration when available.
- **Worker pool** — Node `worker_threads` for CPU parallelism on the TS baseline; pluggable backend interface so CUDA shell-out slots in cleanly.
- **Progress reporting** — callback / AsyncIterator surface emitting `{ attempts, elapsed_ms, estimated_remaining_ms }`. User can set a budget (time or attempts) and abort cleanly via AbortSignal.
- **Security boundary** — generated keypairs NEVER returned as raw bytes. Output is a `WalletHandle` handed directly to the vault for encryption and storage, or an address + encrypted seed pair written to an operator-controlled path. No plaintext seed ever leaves process memory unwrapped.
- **Determinism for testing** — seeded mode (`deterministicSeed: string`) produces reproducible grind orderings for CI.

### Package `@ap3x/pumpfun-launch` (new)

- **Launch orchestrator** — composes `buildCreate` + optional `buildBuy` legs into a single atomic Jito bundle. Up to 4 buy legs (5-tx bundle limit minus the create). Receipts required for every buy leg; create tx receipt is optional but the launch parameters are audit-logged.
- **LaunchConfig** type — token name, symbol, metadata URI, initial liquidity, creator wallet, optional initial buy parameters per snipe wallet (amount, slippage, priority tier).
- **Bundle composition helpers** — derive ATA accounts, compute expected post-create curve state, bind to buy-leg expected outcomes. Guard tx aborts the whole bundle if any buy leg's simulated state diverges beyond slippage bounds from the actual post-create state.
- **Fail-closed semantics** — bundle composition that can't prove atomicity (e.g., a buy leg whose receipt has expired between simulation and submission) rejects with a typed error before submission.
- **Tier gating** — launches land on the TIER 2 approval path by default (size-proportional soft approval); launches from wallets not yet tagged `graduated_dev` require Tier 3.

### Package `@ap3x/pumpfun-metadata` (new)

- **Read API** — fetch and decode metadata for any pump.fun mint (extends PRP-02's parsers). Returns typed `{ name, symbol, uri, sellerFeeBasisPoints, creators, collection, uses, authorities: { mint, freeze, update } }`.
- **Update flows** — `updateMetadata(mint, patch, authority)` for authority holders. Only writes the fields that changed; preserves the rest.
- **Authority revocation** — `revokeMintAuthority`, `revokeFreezeAuthority`, `revokeUpdateAuthority`. These are IRREVERSIBLE — mandatory Tier 3 (hard human approval) with a thesis that explicitly acknowledges the irreversibility. Audit log captures a permanent record.
- **Trust signal emission** — after a revoke confirms on-chain, emit a `trust-signal` event (e.g. `{ mint, signal: 'mint-authority-revoked', slot, signature }`) that PRP-04's signal layer can ingest to raise the mint's rug scorecard.

### Package `@ap3x/pumpfun-airdrop` (new)

- **Snapshot** — given a mint and an `asOf` slot, produce a list of holders + balances. Pluggable filters: top-N holders, holders with a specific tag from PRP-04.5's label system (`smart_money`, `kol`, `fresh`, etc.), holders above/below a balance threshold, holders active within a time window.
- **Distribution planner** — given a snapshot + a distribution scheme (flat amount, proportional to holding, square-root scaled, custom rule), produce a distribution plan as a list of `(destination, amount)` pairs. Reviewable before execution.
- **Bundle executor** — batch transfers through Jito bundles (5 transfers per bundle). Runs as a single policy-gated operation: total aggregate amount counts against daily SOL / token budget; each bundle is audit-logged as one composite action with the full plan attached.
- **Resumability** — distribution plans are idempotent. If bundle 7 of 50 fails to land, the resume command replays only bundles 7+. State persisted to disk via `FileStrategyStateStore` from PRP-02.

### Integration with PRP-03 policy engine

- All four packages register their tool schemas with `@ap3x/pumpfun-policy`. No new policy engine — reuses what PRP-03 ships.
- New tool schemas: `simulate_launch`, `submit_launch`, `update_metadata`, `revoke_authority`, `plan_airdrop`, `execute_airdrop`.
- Tier assignments per operation:
  - Vanity address generation: Tier 0 (no on-chain write)
  - Launch: Tier 2 (soft approval)
  - Launch from untagged dev wallet: Tier 3 (hard approval)
  - Metadata update: Tier 1 (auto, logged)
  - Authority revocation: Tier 3 (hard approval, thesis must acknowledge irreversibility)
  - Airdrop plan: Tier 0
  - Airdrop execute: Tier 2 with a per-operation cap separate from daily trading budget

2. CLI commands: `ap3x-pumpfun vanity`, `ap3x-pumpfun launch`, `ap3x-pumpfun metadata`, `ap3x-pumpfun airdrop` — each wrapping the package's primary entry point with argv parsing + operator-friendly output.

## Acceptance criteria (gate)

1. **Vanity grind performance** — TypeScript baseline hits a 4-character prefix on an M3 Mac in under 60 seconds (median of 10 runs); CUDA shell-out hits it in under 5 seconds when available. Documented scaling table: 4 char / 5 char / 6 char / 7 char expected times.
2. **Launch bundle atomicity** — a launch+snipe bundle lands atomically in a single Jito bundle; the mint creation and all buy legs appear in the same slot. Verified on devnet across 10 test launches.
3. **Guard-tx revert protection** — when curve state is injected with drift between sim and land, the guard tx aborts the bundle; no partial execution observed. Verified via fork slot replay.
4. **Authority revocation is irreversible** — integration test confirms the operation cannot be undone by any platform-exposed tool. Audit log entry includes the thesis field and a permanent record marker.
5. **Airdrop completeness** — distribution to 500 wallets completes via 100 bundles (5 transfers each) in under 2 minutes on devnet. Resume after simulated failure at bundle 47 successfully replays bundles 47-100 with no duplicates.
6. **Receipt + policy + audit integrity** — all write operations verified by fuzz test to require live receipts; all Tier 1+ operations verified to produce audit log entries with thesis populated.
7. **Zero plaintext seed exposure** — security audit of the vanity package confirms no code path allows a generated seed to leave process memory unencrypted.

## Key design decisions

- **Vanity grinding is a separate utility, not on the trading hot path.** No performance constraints beyond reasonable UX. Grind workloads that run for hours are legitimate use cases; the platform manages them, doesn't optimize for them.
- **Launch bundles reuse the Jito bundler from PRP-03.** No new submitter. The launch orchestrator is a thin composition layer over existing primitives.
- **Metadata and authority operations are writes.** Treat them identically to buys/sells — receipts required, policy gates applied, audit log populated with thesis.
- **Authority revocation is Tier 3 + irreversibility acknowledgment.** This is a one-way door; the policy gate enforces operator intent is explicit.
- **Airdrops batch through bundles, not parallel submissions.** Maintains ordering, lets the policy engine reason about the whole operation as one action, preserves resume semantics.
- **Trust signals feed PRP-04.5's scorecard.** Revoking mint authority is a meaningful trust commitment; the signal layer should know about it to raise the mint's rug scorecard accordingly.

## Risks + open questions

| Risk | Mitigation |
|---|---|
| Vanity grind CPU cost scales exponentially with prefix length | Document clearly (4 char ≈ seconds, 6 char ≈ minutes, 8 char ≈ hours on TS baseline); offer CUDA shell-out for power users; enforce a default time budget with explicit opt-in for longer grinds |
| Launch+snipe bundle may miss landing if Jito tip is too low | Inherit PRP-03's dynamic tip ceiling; fail-closed if simulation's implied tip exceeds configured max |
| Authority revocation mistakes are permanent | Tier 3 hard approval + explicit irreversibility thesis; no CLI one-liner; UI flow requires typed confirmation of the address |
| Airdrop runs blow through daily SOL budget | Separate airdrop budget cap from daily trading budget in policy config; operator sets both explicitly |
| Metadata update races with other operations | Per-mint mutex on metadata operations; serialized through a per-mint queue (mirror `InstanceQueue` from PRP-02) |
| Vanity grinding leaks seeds via error messages / stack traces | Strict type discipline — seeds are never strings, always `Uint8Array` inside a handle; error formatters redact by default; unit test every error path |

## Key design decisions revisited — what NOT to build

- **Not vanity address grinding for wallets you don't own.** The API accepts a user-provided vault + grinds a keypair directly into it. No "grind and deliver" that could expose the seed.
- **Not launch templates / UI builders.** This is a primitives layer. A "launch wizard" consumer product can sit on top; it's not platform work.
- **Not metadata editing on tokens you don't hold the update authority for.** The API will reject attempts; no social engineering surface.
- **Not airdrop distribution to wallets the platform suggests.** Operator must provide the snapshot filter explicitly. No "smart airdrop targets" auto-generated from behavior — that edges toward market manipulation.
