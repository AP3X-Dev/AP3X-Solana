# PRP-03.6 — Multi-wallet OpSec

**Repo:** `ap3x-solana/` (continues from PRP-03)
**Depends on:** PRP-03 (execution + safety), PRP-02 (strategy runtime)
**Unblocks:** PRP-08 (strategy SDK gets multi-wallet primitives for free)
**Estimate:** 2-3 weeks solo
**Master spec:** [00-master-platform-prp.md](./00-master-platform-prp.md)

## Goal

Ship first-class **multi-wallet management** with role-based assignment, SOL routing between owned wallets, distributed strategy execution, and scheduled address rotation. This is the platform-sanctioned OpSec surface — legitimate capability that many operators need (treasury management, strategy IP protection, anti-copy-trader defense, physical safety) without crossing into anti-detection tooling the platform is not willing to own.

The architectural insight: multi-wallet is useful **independent of any privacy framing**. Allocation across wallets, role-based routing (hot / warm / cold / burner), address rotation for hygiene, distributed strategy execution — these are capabilities every serious operator wants. Ship the primitives; let users build the meta-strategies on top.

## In scope

### Package `@ap3x/wallet-pool` (new)

- **WalletPool abstraction** — manages N vault handles as a single coordinated pool. Each wallet carries typed metadata: `role` (`hot` / `warm` / `cold` / `burner` / `hop`), `created_at`, `funding_source` (tracked via metadata at unlock time), `last_active_at`, operator-set tags.
- **Assignment policies** — pluggable rules for "which wallet executes this operation":
  - `round-robin` — fair rotation across eligible wallets
  - `weighted` — bias toward specific wallets (by balance, age, or operator weight)
  - `role-gated` — only wallets with a matching role are eligible
  - `least-recently-used` — spread activity temporally
  - Custom — operator-provided predicate function
- **Balance + activity tracking** — per-wallet balance snapshots (pulled from RPC), activity heatmaps, idle detection. Useful for rotation triggers and capacity planning.
- **WalletHandle composition** — seamlessly integrates with PRP-03's `resolveWallet` injection seam. `WalletPool.resolve(role?)` returns a `WalletHandle`.
- **Persistence** — pool membership, role assignments, and metadata persisted to `FileStrategyStateStore` (PRP-02) or a pluggable backend. Pool state survives restarts.

### Package `@ap3x/hop-router` (new)

- **SOL-only HopRouter** — route SOL between owned wallets via multi-hop paths. Input: `(source: WalletHandle, destination: WalletHandle, amountLamports, options)`. Output: a `HopPlan` — a list of intermediate hops with per-hop timings, amounts, and optional noise legs.
- **Hop plan shape:**
  ```ts
  interface HopPlan {
    id: string;                    // deterministic from inputs + seed
    legs: HopLeg[];
    totalDelayMs: number;          // sum of per-leg delays
    totalFeeLamports: bigint;      // estimated cost of all legs
    auditTrail: HopAudit[];        // populated as legs execute
  }
  interface HopLeg {
    from: WalletHandle; to: WalletHandle;
    amountLamports: bigint;        // jittered from input by per-leg amount
    scheduledAt: number;           // absolute timestamp (ms)
    noiseTx?: NoiseTxSpec;         // optional decoy leg
  }
  ```
- **Jitter + delay parameters** — operator configures minimum/maximum per-leg delay (default 5-90 minutes), amount jitter (default ±2%), whether to include noise legs.
- **Policy integration** — every HopRouter operation is policy-gated:
  - Depth 1-2 (single hop, direct route): Tier 1 (auto, logged)
  - Depth 3: Tier 2 (soft approval)
  - Depth >3: Tier 3 (hard approval)
  - Any hop targeting a wallet NOT in the caller's `WalletPool`: **blocked by construction** (type system rejects the call)
- **Audit trail** — every leg audit-logged with thesis, source, destination, amount, and the full plan ID for correlation. Plan-level summary entry too.
- **Resumability** — plan execution survives restart. State in `FileStrategyStateStore`; a plan that crashed mid-execution resumes from the last confirmed leg.
- **Deterministic mode for testing** — seeded jitter / timing produces reproducible plans for CI.

### Package `@ap3x/solana-strategy` addition — `DistributedStrategy`

- **`DistributedStrategy` class** — runs one strategy logic across N wallets with pluggable assignment rules. Signal handling:
  - `onSignal` fires for the strategy's configured filter; the `DistributedStrategy` routes it to one or more wallets via the assignment policy.
  - Each wallet has its own `InstanceQueue` (reusing PRP-02's per-instance FIFO), so ordering is preserved per wallet while different wallets run concurrently.
  - Per-wallet state (`StrategyStateStore` scoped to `(strategyName, instanceId, wallet)`) isolates wallet-specific position tracking.
- **Assignment rules** — `AssignmentPolicy`:
  - `all` — every eligible wallet responds to the signal (use case: coordinated buy across a bundle group)
  - `one-of` — exactly one wallet handles it; pick by assignment policy (use case: spread trading activity)
  - `subset` — N of M wallets respond (use case: partial exposure)
  - `conditional` — operator-provided predicate per signal/wallet
- **Per-wallet timing variance** — when `all` or `subset`, each wallet can delay its action by a jittered amount (default ±5s) to avoid identical-timestamp clustering. Jitter is strategy-level policy, not baked into the runtime.
- **Per-wallet sizing** — each wallet's action amount can be independently sized (operator supplies a `sizeFor(wallet, signal)` function). Defaults to equal split.
- **Cross-wallet state sharing** — optional shared state store scoped to the strategy name; wallets can read shared state for coordination without losing per-wallet isolation.

### Package `@ap3x/pumpfun-policy` additions

- **Multi-wallet policy extensions** — new tool schemas and tier rules:
  - Coordinated multi-wallet buy (N wallets, same mint, same slot window): Tier 2
  - Coordinated multi-wallet exit: Tier 2
  - Hop chain depth ≤3: Tier 1/2 per depth
  - Hop chain depth >3: Tier 3
  - Hop through non-owned intermediate: **blocked by construction** (can't happen)
  - Address rotation (scheduled consolidation): Tier 1 if within daily budget, Tier 2 otherwise
- **Aggregate exposure enforcement** — existing `per_wallet_aggregate_open_exposure` cap from PRP-03 extends to `per_pool_aggregate_open_exposure` — the pool's total SOL + open position value across all wallets.

### Address rotation scheduler

- **Rotation policies** — operator-configured rules:
  - Age-based: hot wallets older than N days auto-consolidate profits to cold, then mark deprecated
  - Threshold-based: when a hot wallet's cumulative profit exceeds X SOL, consolidate
  - Manual: operator triggers rotation explicitly via CLI
- **Consolidation flow** — sweep profits from hot wallets to a designated cold wallet. Uses HopRouter under the hood for multi-leg routes when configured. Audit-logged with thesis.
- **Lifecycle state** — wallets progress through states: `active` → `consolidating` → `deprecated`. Deprecated wallets can still sign (for residual cleanup) but are not eligible for new activity assignments.

## Out of scope

- **CEX / bridge integrations for true graph-breaking** — the only way to actually break the on-chain graph is to route through an exchange. Platform does not ship CEX integrations for this purpose. Users who want this write it themselves against the vault API.
- **Behavioral randomization / noise traffic** — making a wallet "look organic" by emitting random-looking transactions is meta-strategy territory. Platform provides the primitives (`WalletPool.resolve` returns any wallet; strategies can send whatever they want); the meta-strategy of *what* to send is user code.
- **Funding graph obfuscation at wallet creation** — disparate funding sources (different CEX withdrawals, different bridges, different timings) requires CEX/bridge integrations. Out of scope for the same reason.
- **Anti-clustering meta-strategies** — explicitly not a platform feature. Users who want to build this on top of the primitives may do so; the platform does not ship it, document it, or market it.
- **Mixing / tumbling services** — Tornado Cash-equivalents on Solana. Categorically excluded; not a future work item, not on the roadmap.
- **Wash trading tooling** — coordinating buys + sells between owned wallets on the same mint for fake-volume purposes. PRP-03's policy engine flags same-mint opposing-side operations from the same pool as Tier 3 by default; this PRP does not relax that.

5. Examples:

6. Documentation — `docs/multi-wallet-opsec.md` with:
   - API reference
   - Operational workflows (pool setup, role assignment, rotation scheduling)
   - **Explicit "what this is and isn't"** section: what legitimate OpSec use cases this supports, what use cases are out of scope and why, what users building those should know

## Acceptance criteria (gate)

1. **Pool scalability** — WalletPool supports 50+ wallets with role-based assignment; `resolve(role)` latency p95 < 5ms; pool state loads from disk in <1s for 100 wallets.
2. **HopRouter determinism** — same inputs + same seed → identical hop plans across runs. Verified by CI regression test.
3. **Policy enforcement under injection** — fuzz test attempts:
   - Depth-3 hop without Tier 3 approval → rejected
   - Hop targeting a non-pool wallet → rejects at compile time (type system) and runtime (defense in depth)
   - Aggregate pool exposure breach → rejected
   All attempts verified blocked.
4. **Distributed strategy isolation** — two DistributedStrategy instances with overlapping wallet sets maintain independent state per (strategy, wallet); no cross-contamination verified by integration test.
5. **Per-wallet serialization preserved** — DistributedStrategy wraps each wallet in its own InstanceQueue; signals for one wallet serialize FIFO within that wallet while different wallets run concurrently. Verified by instrumented test.
6. **Rotation reliability** — scheduled rotation runs for 7 days on devnet without missed rotations, without incorrect wallet state transitions, without audit-log gaps.
7. **Resumability** — hop plan execution that crashes after leg 5 of 10 resumes from leg 6 on restart; no duplicate legs, no skipped legs. Verified by injection test.
8. **Zero plaintext seed exposure through pool API** — all pool operations return WalletHandles, never raw keys. Security audit confirms.

## Key design decisions

- **WalletPool is the right primitive regardless of OpSec framing.** Multi-wallet allocation, role-based operations, rotation, and per-wallet sizing are legitimate capabilities every serious operator needs. Framing the package around these use cases keeps the marketing clean and the legal posture grounded.
- **HopRouter is SOL-only and owned-intermediates-only.** Two constraints that hold the line:
  1. SOL-only — routing tokens through multiple hops is not a feature. Tokens have tax implications per-hop and create audit nightmares; stick to SOL.
  2. Owned-intermediates-only — the router cannot route through a wallet the caller doesn't own (enforced at the type level: `HopRouter.route` takes `WalletHandle[]` for intermediates, not addresses). Prevents the "send my SOL to your wallet then to theirs" pattern that courts call layering.
- **DistributedStrategy uses per-wallet InstanceQueue.** PRP-02's per-instance FIFO serialization is the right mechanism for per-wallet serialization — same invariants, same guarantees, zero new runtime code.
- **Policy gates at the tier layer, not at the package layer.** Nothing in `@ap3x/wallet-pool` or `@ap3x/hop-router` enforces policy directly. The `@ap3x/pumpfun-policy` package (PRP-03) holds all tier rules; this PRP just registers new schemas. Keeps policy decisions in one place.
- **No CEX/bridge integrations.** The line the platform holds. Users who want to build CEX-hop workflows do so at the strategy layer using their own code + credentials; the platform provides the primitives but does not package the escape hatch.
- **No meta-strategies.** Anti-clustering, behavioral mimicry, funding obfuscation — all meta-strategies that compose the primitives. Users can build them; the platform doesn't ship them.

## Risks + open questions

| Risk | Mitigation |
|---|---|
| Marketing positioning drift — "multi-wallet OpSec" tips into "anti-detection platform" in public materials | Documentation explicitly scopes capabilities; package naming (`wallet-pool`, `hop-router`, not `privacy-*` or `evasion-*`) signals intent; CLAUDE.md rule for commit messages avoids any language that frames features as evasion tools |
| Hop chains audit-confusing for operators reviewing logs | Every leg audit entry correlates to the parent plan ID; plan-level summary entry shows the full route at a glance; CLI `ap3x-audit show-plan <id>` renders the plan tree |
| Users extend toward behavioral randomization and expect platform support | Docs explicitly state the scope line; any GitHub issue asking for behavioral-randomization features gets a documented "not a platform feature" reply |
| DistributedStrategy assignment policies get hairy with 50+ wallets | Profile + benchmark at scale in CI; assignment policy evaluation must stay O(1) or O(log N) per operation; reject policies that would be O(N²) |
| Rotation scheduler races with active strategies | Rotation runs as a serialized operation through the same per-wallet queue that strategies use; can't race by construction |
| Pool state file corruption across process crashes | Atomic tmp+rename + per-wallet mutex from PRP-02's conventions; integrity-check on load with self-repair for known patterns |

## Platform positioning statement (for docs)

**What this ships:** first-class multi-wallet management, SOL routing between wallets you own, distributed strategy execution, scheduled rotation.

**What this doesn't ship:** anti-detection tooling, behavioral obfuscation, wash-trading coordination, mixing services, CEX-hop integrations. The primitives are neutral; the meta-strategies are user territory.

**Who benefits:** treasury managers protecting fund wallets from targeted attacks. Strategy authors preserving edge against parasitic copy-traders. Operators in adversarial regions managing physical-safety exposure. Every user running more than one wallet for any reason.

**Who this isn't for:** anyone whose primary use case is regulatory evasion, market manipulation cover, or sanctions evasion. The platform cannot prevent determined adversaries from composing the primitives into those uses, but it does not market, document, or endorse such uses.
